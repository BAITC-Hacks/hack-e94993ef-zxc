# Smart Contractor

> Объяснимый подбор event-подрядчиков по параметрам конкретного мероприятия.

## 1. Название проекта

**Smart Contractor** — сервис детерминированного подбора подрядчиков с объяснением результата и автоматическим «Планом Б» для слишком строгих запросов.

## 2. Краткое описание

Пользователю сложно вручную сравнивать подрядчиков сразу по городу, дате, формату мероприятия, бюджету, языку и длительности работы. Smart Contractor принимает эти параметры, исключает неподходящие профили и возвращает до трёх релевантных вариантов.

Ценность решения — не только в выдаче кандидатов, но и в объяснении причин выбора. Если подходящих вариантов недостаточно, сервис анализирует ограничения и предлагает минимальное изменение запроса через модуль **«План Б»**.

## 3. Что реализовано

- фильтрация по городу и категории;
- проверка занятости на выбранную дату;
- фильтрация по типу мероприятия;
- проверка бюджета;
- опциональная проверка языка;
- опциональная проверка длительности;
- дополнительные текстовые пожелания;
- TF-IDF + cosine similarity для сопоставления пожеланий с описанием подрядчика;
- детерминированное ранжирование кандидатов;
- выдача максимум трёх карточек;
- 1–2 конкретных объяснения для каждой рекомендации;
- три различимых состояния ответа:
  - `matched` — подходящие подрядчики найдены;
  - `category_absent` — выбранной категории нет в городе;
  - `no_match` — категория есть, но условия не проходит никто;
- диагностика причин исключения кандидатов;
- **«План Б»** — предложения изменить дату, бюджет, язык, длительность, город или сочетание даты и бюджета;
- кнопка применения «Плана Б» с автоматическим повторным поиском;
- отображение `synthetic`, `city_imputed`, `price_imputed`;
- современный адаптивный frontend;
- REST API;
- автоматические unit- и API-тесты.

## 4. Как работает решение

1. Пользователь вводит город, дату, формат мероприятия, категорию и бюджет.
2. При необходимости указывает длительность, язык и текстовые пожелания.
3. Backend выбирает профили нужной категории в нужном городе.
4. К кандидатам последовательно применяются обязательные условия: дата, формат, бюджет, язык и длительность.
5. Прошедшие кандидаты получают детерминированный score.
6. Если есть текстовые пожелания, рассчитывается TF-IDF-сходство с описанием профиля.
7. Кандидаты сортируются по score; при равенстве используются стабильные tie-breaker правила по цене и `id`.
8. Пользователь получает до трёх карточек с конкретными объяснениями.
9. Если подходящих вариантов меньше трёх, модуль «План Б» проверяет альтернативные параметры и возвращает до трёх реально работающих изменений запроса.

Одинаковый запрос приводит к одинаковому порядку результатов.

## 6. Архитектура проекта

Frontend и backend физически разделены по разным папкам:

```text
smart-contractor/
├── backend/
│   ├── __init__.py
│   ├── main.py              # FastAPI, endpoints, раздача frontend
│   ├── models.py            # Pydantic-модели
│   ├── data_loader.py       # загрузка CSV
│   └── recommender.py       # фильтры, ranking, TF-IDF, План Б
│
├── frontend/
│   ├── index.html           # структура интерфейса
│   ├── styles.css           # дизайн и адаптивность
│   └── app.js               # API-запросы, карточки, План Б
│
├── data/
│   └── contractors.csv      # 66 профилей подрядчиков
│
├── tests/
│   ├── test_recommender.py
│   └── test_api.py
│
├── pytest.ini
├── requirements.txt
├── run.bat
├── TEAM_TASKS.md
└── README.md
```

### Взаимодействие компонентов

```text
Пользователь
    ↓
frontend/index.html + styles.css + app.js
    ↓ POST /api/recommend
backend/main.py (FastAPI)
    ↓
RecommendationRequest
    ↓
ContractorRecommender
    ├─ город / категория
    ├─ занятость
    ├─ формат
    ├─ бюджет
    ├─ язык
    ├─ длительность
    ├─ TF-IDF
    ├─ детерминированный ranking
    └─ Plan B analyzer
    ↓
Top-3 + explanations + plan_b
    ↓
JSON → frontend
```

FastAPI также раздаёт содержимое папки `frontend/`, поэтому для локального запуска не нужен отдельный frontend-сервер.

## 7. Установка и запуск

### Требования

- Python 3.11+
- pip

### 1. Клонировать репозиторий

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd <ПАПКА_РЕПОЗИТОРИЯ>
```

### 2. Создать виртуальное окружение

Windows:

```powershell
python -m venv .venv
.venv\Scripts\activate
```

Linux/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Установить зависимости

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Запустить приложение

Windows:

```powershell
run.bat
```

Или на любой ОС:

```bash
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

### 5. Открыть приложение

```text
http://127.0.0.1:8000
```

Swagger:

```text
http://127.0.0.1:8000/docs
```

### 6. Запустить тесты

Из корня проекта:

```bash
python -m pytest -q
```

Благодаря `pytest.ini` тесты также можно запускать, находясь внутри папки `tests`:

```bash
python -m pytest -q
```

## 8. Как проверить решение

### Плотная категория

```text
Город: Алматы
Дата: 15.10.2026
Тип мероприятия: корпоратив
Категория: Ведущий
Бюджет: 1 500 000 ₸
Длительность: 6 ч
Язык: русский
Пожелания: интеллигентный юмор импровизация современная подача
```

Ожидается статус `matched` и до трёх карточек. Повторный запуск должен вернуть тот же порядок.

### Редкая категория

```text
Город: Алматы
Дата: 15.10.2026
Тип мероприятия: свадьба
Категория: Флорист
Бюджет: 500 000 ₸
Язык: русский
Пожелания: авторское оформление цветы
```

Ожидается `matched`; если подходящих профилей меньше трёх, интерфейс объясняет это текстом.

### Запрос без результата + «План Б»

```text
Город: Астана
Дата: 31.12.2026
Тип мероприятия: свадьба
Категория: Ведущий
Бюджет: 300 000 ₸
Длительность: 10 ч
Язык: казахский
```

Ожидается `no_match`. Вместо пустого экрана сервис показывает причины отсева и предлагает «План Б». Кнопка **«Применить»** переносит предложенные изменения в форму и запускает поиск повторно.

### Категории нет в городе

```text
Город: Астана
Категория: Декоратор
```

Ожидается `category_absent`. Если категория существует в другом городе, «План Б» может предложить альтернативный город.

## 9. Данные и интеграции

Источник данных:

```text
data/contractors.csv
```

Используемые поля:

- `id`
- `anon_name`
- `categories`
- `city`
- `city_imputed`
- `synthetic`
- `price_from_kzt`
- `price_imputed`
- `event_formats`
- `languages`
- `max_hours`
- `busy_dates`
- `description`

Датасет содержит 66 профилей. Календарь занятости охватывает период `23.09.2026–31.12.2026`.

Внешние API, облачные БД и LLM-сервисы не используются. Все вычисления выполняются локально.

## 10. Ограничения

- источник данных — локальный CSV из 66 профилей;
- поддерживаются только даты внутри календарного окна датасета;
- бронирование, заявки и уведомления подрядчикам не реализованы;
- нет авторизации и пользовательских аккаунтов;
- нет постоянной базы данных;
- нет административного интерфейса;
- TF-IDF работает на лексическом совпадении и не заменяет полноценные semantic embeddings;
- цена используется как `price_from_kzt`, индивидуальная смета не рассчитывается;
- календари не синхронизируются с внешними сервисами;
- «План Б» ищет альтернативы только внутри имеющихся данных и заданных правил.
